## 已发现的问题

### P1：发布检查只覆盖编辑器当前加载的场景

位置：`Editor/KnowledgeBuildProcessor.cs:17`。

OnPreprocessBuild 通过 FindObjectsByType 查找当前编辑器对象；发现不了未打开但包含在 Build Profiles 中的场景，也发现不了仅由资源动态实例化的 KnowledgeRuntime。没有找到运行时对象就直接返回，可能绕过平台、配置、模型和原生版本检查。设计要求中的基础库与索引指纹校验也没有在该构建处理器中实现。

需要在构建场景处理阶段逐个校验运行时配置，并为动态加载配置提供明确注册/校验入口；补充所配置基础库的存在性、manifest、哈希与索引兼容性检查。

### P2：配置的基础知识库缺失时静默继续

位置：`Runtime/Unity/KnowledgeDeployment.cs:17`、`:27`。

源数据库不存在时 manifest 保持 null，安装任务成功结束。随后运行时可以创建空工作库，表现为初始化成功但缺少本应随包交付的知识。明确禁用基础库和基础库配置错误目前不能区分。

本次已用实际部署方法复现：传入不存在的源数据库和 manifest，方法不抛异常，也没有安装目标数据库。检测没有加载模型。

建议用空 seedDatabase 明确表示不安装；非空但文件缺失应有明确错误或可配置的强制校验策略，而不能无提示跳过。

### P2：章节/页码标题可能错误继承

位置：`Runtime/Core/TokenTextSplitter.cs:40`。

分块扫描到第一个标题便结束标题处理。当一个分块包含第一页和第二页标题时，它只记住第一页；接下来只有第二页正文的分块可能仍标为第一页。正文仍被正确索引，但引用位置不可靠，尤其影响新增加的 PDF、PPT 和工作表位置标记。

本次以注入的字符计数器复现分块逻辑：第一分块含两个页标题，第二分块是第二页正文却得到“第一页”Heading。这是分块元数据检查，不是模型性能或真实分词质量测试。

需要分别处理当前分块来源与下一分块继承的最后章节；若要求精确页级引用，应保存结构化来源位置并避免无标记跨页合并。

### P2：没有有效引用的生成结果仍可作为成功回答返回

位置：`Runtime/Core/KnowledgeService.cs:185`。

当前逻辑剔除无效的 [S编号]，但不会要求存在有效引用。模型省略引用或只生成 [S99] 时，最终可以得到 Citations 为空、InsufficientEvidence=false 的回答。这不足以保证“带来源问答”；有效引用 ID 本身也不等于事实与证据一致。

本次使用明确标注的测试向量/生成提供器复现核心逻辑：有检索证据，但生成结果只有虚构引用，编号清除后仍正常返回且没有有效引用。该检测不代表真实模型在业务问题集上的发生频率。

建议增加引用缺失状态或严格引用模式，并将其纳入 UI 和 API；严格模式可进行受控重试或提示无法形成可追溯答案。事实可靠性另需业务问题集评估。
